Two motivating problems

1 · A query the structure doesn't support

A leaderboard stores 10M scores in a balanced BST (from L04's exercise). Product asks for "what is my rank?" and "show ranks 1000–1100", with frequent score updates.

An in-order walk is \(\Theta(n)\) per query. Rebuilding a sorted array per update is \(\Theta(n)\) per update.

2 · A promise that looked fine on paper

An append-only event log uses a growable array: "append is \(O(1)\) amortized". In production, p99 append latency is 4 µs, but the maximum is 19 ms, and it violates a hard real-time deadline.

Was the \(O(1)\) claim false?

Block A · 00:10–01:00

Augmenting data structures

A method, a theorem, and two classic designs

Refresher: what we need from red-black trees

  • A BST with colours; height \(\le2\log_2(n+1)\) ⇒ search/insert/delete are \(O(\log n)\) worst case (R3).
  • Insert/delete = a BST operation on one root-to-leaf path + fix-up: \(O(\log n)\) recolourings and ≤ 2 rotations (insert), ≤ 3 (delete).
  • Rotations are the only structural changes besides the splice at the bottom.
      y                 x
     / \   right(y)    / \
    x   C  -------->  A   y
   / \     <--------     / \
  A   B     left(x)     B   C
For augmentation we only need these three facts: a logarithmic path, \(O(1)\) rotations per update, and rotations change only the two nodes' children.

The augmentation method (CLRS 17.2)

  1. Choose an underlying structure whose guarantees you want to keep (e.g. an RB tree for worst-case \(O(\log n)\)).
  2. Decide the additional information to store (per node).
  3. Verify it can be maintained by every modifying operation (inserts, deletes, rotations) without increasing their asymptotic cost.
  4. Develop the new operations using that information, and prove them correct.
Maintenance theorem (CLRS Thm 17.1)Let \(f\) be a field in an RB tree such that \(x.f\) can be computed in \(O(1)\) from \(x\)'s own data and the \(f\)-fields of its two children only. Then \(f\) can be maintained under insert and delete without changing their \(O(\log n)\) cost.
WhyA change at node \(x\) affects only the \(f\) values of \(x\)'s ancestors: \(O(\log n)\) of them, each recomputed in \(O(1)\). A rotation changes the children of just two nodes: recompute the lower one, then the upper one, in \(O(1)\).

Order-statistic trees: rank and select in \(O(\log n)\)

Field: \(x.size=x.left.size+x.right.size+1\) (\(nil.size=0\)).

OS-SELECT(x, i)        ▷ the i-th smallest in x's subtree
  r = x.left.size + 1  ▷ rank of x within its subtree
  if i == r  return x
  if i < r   return OS-SELECT(x.left, i)
  return OS-SELECT(x.right, i − r)

OS-RANK(T, x)          ▷ rank of node x in the whole tree
  r = x.left.size + 1 ; y = x
  while y ≠ T.root
      if y == y.p.right
          r = r + y.p.left.size + 1
      y = y.p
  return r
OS-RANK invariantAt the start of each iteration, \(r\) = the rank of \(x\) within the subtree rooted at \(y\).
MaintenanceMoving from \(y\) to its parent \(p\): if \(y\) is a left child, nothing in \(p\)'s subtree outside \(y\)'s precedes \(x\). If \(y\) is a right child, all of \(p.left\) and \(p\) itself precede \(x\): add \(p.left.size+1\). At the root, "rank in \(y\)'s subtree" is the rank in the tree.
Leaderboard: rank \(O(\log n)\); ranks \(i..i+k\): select \(i\), then \(k\) successor steps: \(O(\log n+k)\).

Interval trees: a second case study

Store intervals \([lo,hi]\) keyed by \(lo\). Field: \(x.max\) = the largest \(hi\) in \(x\)'s subtree (local: a max of three values).

Query: find some stored interval overlapping \(q=[a,b]\).

INTERVAL-SEARCH(T, a, b)
  x = T.root
  while x ≠ nil and [a,b] does not overlap x.int
      if x.left ≠ nil and x.left.max ≥ a
          x = x.left
      else
          x = x.right
  return x
Why going left is safe

Going right happens only if \(x.left=nil\) or \(x.left.max<a\). Then every left interval ends before \(a\) and cannot overlap.

Going left with \(x.left.max\ge a\): some interval \(i'\) in the left subtree has \(hi'\ge a\). If none on the left overlaps \(q\), then \(lo'>b\) for that \(i'\). Every interval on the right has \(lo\ge lo'>b\) (BST order on \(lo\)), so none on the right overlaps either. Hence no overlap is lost.

Time \(O(\log n)\): one path.

Amortized analysis

Aggregate · accounting · potential · an advanced example

What amortized analysis is, and is not

DefinitionOperations have amortized costs \(\hat c_i\) such that for every sequence of \(m\) operations starting from the initial state, \[\sum_{i=1}^{m}c_i\le\sum_{i=1}^{m}\hat c_i .\]
  • A worst-case bound on sequences.
  • No probability, no assumption about the inputs.
  • A single operation may cost far more than its amortized cost.
Legacy correction

The old slides: "Amortized analysis provides a more accurate average-case analysis".

Wrong. Average-case analysis averages over a distribution of inputs. Amortized analysis averages over the operations of one worst-case sequence.

StatementGuarantee
average caseprobability over inputs
expectedprobability over our coins
amortizedcertain, per sequence

Aggregate method: the binary counter

A \(k\)-bit counter, INCREMENT from 0. Cost = the number of bits flipped.

A single INCREMENT can flip all \(k\) bits (\(0111\cdots1\to1000\cdots0\)), so the naive bound for \(n\) increments is \(O(nk)\).

Aggregate: bit \(i\) flips every \(2^i\) increments, i.e. \(\lfloor n/2^i\rfloor\) times:

\[\sum_{i=0}^{k-1}\Big\lfloor\frac{n}{2^i}\Big\rfloor<n\sum_{i\ge0}2^{-i}=2n .\]

So the amortized cost is \(<2\) per increment.

Accounting method: dynamic array (doubling)

Append into an array of capacity \(s\). When it is full, allocate \(2s\) and copy the \(s\) items (cost \(s\)), then write (cost 1).

Charge 3 per append:

  • 1 pays for writing the item now;
  • 1 is stored on the item, to pay for copying it at the next resize;
  • 1 is stored to pay for copying one old item, whose own credit was spent at the previous resize.

Right after a resize to \(2s\), the table holds \(s\) items and 0 credit. The \(s\) appends until the next resize bring in \(2s\) credits, exactly enough to copy \(2s\) items.

Credit invariantThe stored credit is always \(\ge0\). That is the only thing an accounting proof must establish: then \(\sum c_i\le\sum\hat c_i=3m\).

Potential method

DefinitionA potential \(\Phi\) maps states to reals. Amortized cost \(\hat c_i=c_i+\Phi(D_i)-\Phi(D_{i-1})\). Telescoping: \[\sum_{i=1}^m\hat c_i=\sum_{i=1}^m c_i+\Phi(D_m)-\Phi(D_0).\] If \(\Phi(D_i)\ge\Phi(D_0)\) for all \(i\), then \(\sum c_i\le\sum\hat c_i\).

Dynamic array (doubling only): \(\Phi=2\cdot num-size\) (with \(\Phi=0\) for the empty array).

  • No resize: \(\hat c=1+2=3\).
  • Resize at \(num=size=s\): \(c=s+1\); \(\Phi\): \(2s-s=s\to2(s+1)-2s=2\); \(\hat c=s+1+2-s=3\).
Legacy correction: the condition is \(\Phi(D_i)\ge\Phi(D_0)\), not "\(\Phi\) cannot be negative". (With \(\Phi(D_0)=0\) the two coincide.)

An advanced example: the logarithmic method

Goal: a dictionary supporting INSERT and SEARCH, built only from static sorted arrays (useful when the static structure is much simpler or faster).

Bentley–Saxe: keep sorted arrays \(A_0,A_1,\dots\), where \(A_i\) is empty or has exactly \(2^i\) items. The non-empty ones follow the binary digits of \(n\).

  • Insert: a new array of size 1; while two arrays of size \(2^i\) exist, merge them into one of size \(2^{i+1}\) (like the counter's carries).
  • Search: binary search in each non-empty array: \(O(\log^2 n)\) worst case.
ClaimInsert costs \(O(\log n)\) amortized.
Proof (aggregate / per-element charging)A merge into \(A_{i+1}\) costs \(O(2^{i+1})\), i.e. \(O(1)\) per element moved. Each element only moves to higher levels, and there are \(\le\log_2 n+1\) levels. So over \(n\) inserts the total is \(O(n\log n)\).
Worst single insert: \(\Theta(n)\) (a carry chain of all levels). The latency spike again.

De-amortization: worst-case \(O(1)\) append

Idea: do the copying incrementally. When the array of capacity \(s\) is half full, allocate the next array (capacity \(2s\)). Then, on every append:

  1. write the new item into both arrays (or only the new one, tracking a boundary);
  2. copy 2 old items from the old array to the new one.

By the time the old array is full (\(s/2\) more appends), all \(s/2\) old items have been copied, and we switch arrays in \(O(1)\).

ResultEvery append is \(O(1)\) worst case (ignoring allocation cost). The same total work is spread evenly.
CostsTwo arrays alive (more memory); every operation slightly slower; more complex code (reads must know which array holds each index). Allocation of \(2s\) may itself not be \(O(1)\) (the OS may zero pages).
The same pattern: incremental rehashing in Redis's dictionaries; incremental garbage collection.

Groups · 12 min

Synthesis

  1. Augment with fields computable from the node and its children ⇒ maintained in \(O(\log n)\), including rotations. Non-local fields (depth, global rank, successor) are not.
  2. Order-statistic trees: rank/select \(O(\log n)\) worst case; interval trees: overlap queries with a proof of why one path suffices.
  3. Amortized = a worst-case bound on sequences. Aggregate / accounting (credit ≥ 0) / potential (\(\Phi(D_i)\ge\Phi(D_0)\)).
  4. Amortized bounds hide spikes. When single operations matter, de-amortize or pre-allocate.
