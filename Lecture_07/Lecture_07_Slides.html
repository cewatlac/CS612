Weighted interval scheduling

Intervals \(j=1..n\) sorted by finish time, with values \(v_j\). Choose compatible intervals of maximum total value.

\(p(j)\) = the largest index \(i<j\) with \(f_i\le s_j\) (0 if none): computable by binary search.

\[OPT(j)=\max\big(OPT(j-1),\ v_j+OPT(p(j))\big),\quad OPT(0)=0.\]

Last decision: is interval \(j\) (the last to finish) in the solution? If yes, the rest is an optimal solution among intervals compatible with \(j\), namely \(1..p(j)\). If no, it is an optimal solution among \(1..j-1\).

\(O(n\log n)\): sort + binary searches; the DP itself is \(O(n)\).

Why not greedy?Earliest finish is optimal for the unweighted version (L01, L08). With weights: \([0,10)\) of value 10 vs. \([0,1),[1,2)\) of values 1, 1. Earliest finish takes 2, but the optimum is 10. Greedy by value or by value/length also fails (exercise).
Modelling pointSorting by finish time is what makes "the last interval" a well-defined last decision, and makes the state a single index.

LIS: changing the state changes the complexity

State 1 (L06): \(E[i]\) = the LIS length ending at \(i\). \(E[i]=1+\max_{j<i,a_j<a_i}E[j]\): \(O(n^2)\).

State 2: after processing \(a_1..a_i\), let

\[T[k]=\min\{\text{last element of an increasing subsequence of length }k\}.\] 
LIS(a)
  T = empty array
  for x in a
      k = first index with T[k] ≥ x    ▷ binary search
      if none: append x to T
      else:    T[k] = x
  return length(T)
Invariant\(T\) is strictly increasing, and \(T[k]\) has the meaning above for the processed prefix.
MaintenanceA new \(x\) can extend exactly the subsequences whose last element is \(<x\). The longest such has length \(k-1\), where \(k\) is the first index with \(T[k]\ge x\). So a length-\(k\) subsequence ending in \(x\) exists, and \(x\le T[k]\) improves (or keeps) \(T[k]\). No other entry can improve. Strictness is kept because \(T[k-1]<x\le T[k]\).
\(O(n\log n)\). The state changed from "position" to "best tail per length": a dominance argument. Only the smallest tail per length matters.

Three ways to make a DP cheaper

TechniqueIdeaExample
State reductionRemove information the future does not need, or merge dominated statesLIS \(E[i]\to T[k]\); knapsack Pareto lists (Block B)
Transition optimisationCompute each \(\min/\max\) over predecessors faster, using monotonicity or a data structurebinary search (LIS, weighted intervals); prefix-max with a Fenwick tree; Knuth's optimisation for interval DPs (\(O(n^3)\to O(n^2)\)); convex-hull trick
Space optimisationKeep only the part of the table the evaluation order still needstwo rows for LCS/edit distance; one row for knapsack (iterate \(c\) downwards); Hirschberg for reconstruction
Each technique needs its own correctness argument: a monotonicity lemma, a dominance lemma, or a proof that the discarded values are never read again.

Knapsack and pseudo-polynomial time

Correctness · space · memo vs. tabulation · dominance · encoding

0/1 knapsack: the DP and its correctness

Items \(1..n\) with integer weights \(w_i\) and values \(v_i\); capacity \(W\).

State: \(K[i][c]\) = the maximum value using a subset of items \(1..i\) with total weight \(\le c\).

\[K[i][c]=\max\big(K[i-1][c],\ v_i+K[i-1][c-w_i]\ (\text{if }w_i\le c)\big),\quad K[0][c]=0.\]

Time \(\Theta(nW)\) · space \(\Theta(nW)\) → \(\Theta(W)\):

for i = 1 to n
    for c = W downto w[i]          ▷ downwards!
        K[c] = max(K[c], K[c − w[i]] + v[i])
AskWhy must \(c\) go downwards in the 1-D version? What problem do you solve if it goes upwards?
Greedy failsBy value density: \(W=10\); items \((w,v)=(6,7),(5,5),(5,5)\). Densities \(1.17,1,1\): greedy takes item 1 (value 7) and nothing else fits; the optimum is items 2+3 (value 10). Greedy is optimal for the fractional knapsack.

Memoization vs. tabulation: an engineering decision

Memoization (top-down)Tabulation (bottom-up)
States computedonly those reachable from the goalall states in the table
Evaluation orderimplicit (recursion)must be designed (topological)
Space reductionhard (needs every cached state)easy (rows/diagonals)
Overheadsrecursion, hash map lookups, stack depth \(O(n)\)tight loops; cache-friendly; vectorisable
Knapsack with huge \(W\) but few itemsvisits \(\le\min(nW,\,2^{n+1})\) statesallocates \(nW\) regardless
Neither choice changes the worst-case bound. They differ in which states are touched, memory, and constants. Choose by the sparsity of the reachable states and by memory limits.

Dominance: Pareto sets instead of a \(W\)-sized table

Represent the partial solutions over items \(1..i\) as (weight, value) pairs. Pair \((w,v)\) dominates \((w',v')\) if \(w\le w'\) and \(v\ge v'\). A dominated pair can never lead to a better final solution: discard it.

P0 = {(0,0)}
for i = 1 to n
    Q = P(i−1) ∪ {(w + w_i, v + v_i) : (w,v) ∈ P(i−1), w + w_i ≤ W}
    P(i) = the non-dominated pairs of Q   ▷ merge of 2 sorted lists: O(|Q|)

Time \(O\big(\sum_i|P_i|\big)\) (Nemhauser–Ullmann 1969). Worst case exponential, but independent of \(W\), and often small on real data.

Value-indexed DPIf values are small integers: \(M[i][v]\) = the minimum weight to achieve value exactly \(v\) with items \(1..i\). \(O(n\cdot\sum v_i)\) time, independent of \(W\). This is the basis of the knapsack FPTAS (L14): round the values, then use this DP.
Which one to use depends on which number is small: \(W\), \(\sum v_i\), or the Pareto frontier.

Input size and pseudo-polynomial time

DefinitionsAn algorithm is polynomial if its running time is polynomial in the input length (bits). It is pseudo-polynomial if it is polynomial in the input length and the numeric values of the input, equivalently, polynomial when the numbers are written in unary.
  • Knapsack input: \(O(n\log W+\sum_i(\log w_i+\log v_i))\) bits.
  • \(O(nW)=O(n\cdot2^{\log W})\): exponential in the bits of \(W\).
  • Polynomial when \(W\le n^{c}\) (or the numbers are given in unary).

Consequence (L13): knapsack and subset sum are NP-complete, but only weakly. Their hardness needs large numbers. Strongly NP-hard problems (e.g. TSP, 3-partition) stay hard even with numbers bounded by a polynomial in \(n\).

A pseudo-polynomial algorithm does not prove P = NPAn \(O(nT)\) algorithm for subset sum is exponential on instances with \(T\approx2^n\), which are exactly the hard instances produced by the NP-hardness reduction (L13).

Synthesis

  1. A better state can change the complexity (LIS: \(n^2\to n\log n\) via dominance).
  2. Optimise in three ways: state reduction, transition speed-ups (monotonicity, data structures), space reduction. Each needs its own proof.
  3. Memoization vs. tabulation: same worst case; different reachable states, memory and constants.
  4. Knapsack: \(O(nW)\), \(O(n\sum v)\), Pareto lists, meet-in-the-middle. Choose by which number is small.
  5. Pseudo-polynomial = polynomial in the numeric values, exponential in their bit length. That is the gateway to weak vs. strong NP-hardness.
